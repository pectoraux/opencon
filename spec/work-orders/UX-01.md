# Work Order UX-01 — Unified product client experience

**Status:** FROZEN — proposed under the architect-approved OpenCon Unified Product UX brief  
**Issue:** to be created on merge (implementation already delivered in the product client environment; this PR is the governance record)  
**Dependencies:** none (consumes the versioned API contract; W001–W036 authoritative behavior)  
**Architecture:** v1.0 FROZEN — no architecture amendment, no new domain boundary

## 1. Objective

Deliver the approved unified product UX as **one coherent adaptive client**:

```text
Home ── What matters to me right now?
Discover ── What can I participate in?
Work ── What am I currently doing?
Wallet ── What did I create, what is pending, what can I use?
You ── Who am I in OpenCon?
```

The user must never be required to understand the protocol's authorities to use
OpenCon. The client is a consumer of the versioned product API and holds no
authority of any kind.

## 2. Non-negotiable constraints

1. The frontend MUST NOT: compute authoritative settlement values locally; create
   lifecycle states; invent rights, campaign-policy or evidence truth; treat AI
   output as authoritative; persist a second copy of economic state; or bypass
   APIs to manipulate domain state.
2. Lifecycle facts arrive with the authoritative state vocabulary (architecture
   §17) and are translated for display; the authoritative state remains visible
   on advanced surfaces.
3. Value phases are settlement-owned; pending value is never presented as
   spendable; uncertainty and delay reasons are preserved.
4. Evidence status is authority-owned; uploaded never implies verified.
5. Action availability is decided server-side; rejections surface human reasons.
6. Cross-tenant/unknown objects fail closed with no existence oracle.
7. No W036/W037 protocol behavior, no second ledger, no new lifecycle engine,
   no seventeenth domain, no changes to frozen architecture files.

## 3. Scope

- App shell: desktop sidebar / mobile bottom bar over the five destinations;
  global search; notifications grouped by intent (Needs you / Updates /
  Results / Money / Trust) with deep links.
- Universal object grammar: Opportunity card, Work item card, transaction row;
  universal detail grammar (Overview / Your task / Requirements / Evidence /
  Outcome / Value / History / Details / Help) with progressive disclosure.
- Human lifecycle translation with exceptional states (blocked, additional
  verification, under challenge) never concealed.
- Role adaptation: one identity, Personal · Creator · Business contexts.
- Creation flow: campaign wizard (objective → audience → budget/measurement →
  review → activate) — minimal fields, sensible defaults.
- Empty, loading and error states that answer: what happened, can I fix it,
  what happens next.
- Accessibility: keyboard navigability, landmarks, labels, visible focus,
  no color-only status, reduced-motion-safe transitions, 44px touch targets.

## 4. Out of scope

- Any backend authority or protocol behavior change.
- Real provider wiring (measurement/payment/LLM) — advisory copy only.
- The production versioned product API itself (documented as a gap).

## 5. Acceptance criteria

- AC-01 All five destinations render with live data and coherent hierarchy.
- AC-02 The creator journey is completable end-to-end through the UI
  (accept → rights → disclosure → submit → verification → value → payout).
- AC-03 The advertiser journey (wizard → live campaign → end → measured →
  settled) and the dispute journey (respond → resolved → value released) work.
- AC-04 Eligible benefits are claimable; ineligible benefits are rejected with
  the server's eligibility reason.
- AC-05 Unauthorized actions are rejected by the server boundary and the human
  reason is surfaced; pending value is never spendable; payout is offered only
  for matured value.
- AC-06 Cross-tenant and unknown objects fail closed identically.
- AC-07 Mobile (≤ 390px) has no horizontal overflow; footer sticks on short
  pages and is pushed naturally on long pages; desktop uses the sidebar shell.
- AC-08 Interaction-path tests cover the lifecycle translation, money
  semantics, guards and journeys.
- AC-09 Architecture regression: zero new `arch:check` violations; frozen
  architecture files byte-identical; no `src/{core,domain,infra,adapter}`
  changes.
- AC-10 The client consumes only the product API through one fetch layer; no
  domain module is imported by the client.
